# 特征研究协议

语言：简体中文 · [English](feature-research-protocol.en-US.md)

当研究范围、标签、评估设计、回测规则和市场数据都已固定，而问题集中在特征组能否提供有效证据时，可以按本页流程做对照。每次只改变一项特征选择，便于解释结果变化。

本页介绍可复用的研究流程。具体策略假设、专有特征集合和晋升决策应记录在所属研究项目中，不作为通用平台指南的承诺。

## 对比特征组

可按特征用途分组，例如动量、流动性、估值、盈利能力或数据新鲜度。这些只是分类示例，不是固定目录。请在实验配置中记录实际特征名和分组依据。

先运行基线，再逐组移除特征。基线和对照应使用相同的样本范围、标签、评估窗口、交易成本和回测设置。单个特征的重要度排名不能单独证明该特征有独立价值。

`alpha_research.feature_evidence.generate_ablation_jobs` 会生成基线配置、每个特征组对应的配置和 `jobs.csv` 任务计划，但不会执行任务。汇总函数读取已完成的运行结果，并计算各项指标相对基线的变化。该辅助模块读取 `feature_evidence` 配置。生成消融配置时，`base_config` 所指文件必须包含 `features.list`。

这些辅助函数没有注册为 `strategy-pipeline` 命令。当前 CLI 提供 `afml-evidence` 和 `research-protocol`，但没有 feature-evidence 命令。旧的 `strategy alpha feature-evidence` 示例不可用。

## 添加稀疏输入前先检查覆盖率

如果某项特征只覆盖部分历史，先检查覆盖率，再解释模型结果。数据集构建器在可用性显著下降时可能记录 `Feature availability collapse before complete-case filter`。也要比较其他条件相同的实验保留了多少日期和样本。

零特征重要度和预测值恒定是需要调查的诊断信号，不是自动晋升或否决条件。结合样本外指标、换手、成本和可用的特征稳定性结果一起判断。

## 保持对照可解释

- 每次只调整待检验的特征列表或特征组。
- 基线和消融组使用相同的数据与评估契约。
- 保留生成的配置和已完成运行的路径。
- 下结论前检查覆盖率、样本外结果、换手和成本。
- 明确标注探针和诊断实验，不要将其描述为生产建议。
